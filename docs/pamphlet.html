Executive summary

A buying agent you can actually trust with a budget

AgentCart is a working agentic-checkout prototype built on PayPal's sandbox. It demonstrates one idea precisely: an AI agent can be given real purchasing power if — and only if — its authority is bounded by code and released by a human.

tool exposed to the model: create_order
4
independent trust layers before money moves
2
checkout paths: agentic and deterministic
0
captures possible before human approval

What we built

A single-page Next.js app. A user gives the agent an errand and a spend cap. The agent chooses an item from a fixed catalog, creates a PayPal order through the Agent Toolkit, and stops. The browser sends the user to PayPal's sandbox approval screen. On return, the server captures the payment and renders a receipt containing the real order ID, capture ID, payer, and amount.

Around that happy path sit four defence layers: a server-side spend cap, a merchant and price allowlist, a human approval gate that the model cannot bypass, and a timestamped audit trail. A deterministic fallback can complete the same flow without any LLM, using the same PayPal APIs.

Why it matters

The hard problem in agentic commerce is not teaching a model to click "buy". It is granting delegated authority without granting unbounded risk. Most prototypes either keep the human clicking every button — which is not agency — or hand the model a full payments toolkit and hope the prompt holds.

This design takes the third path: the model gets exactly one irreversible-adjacent capability, and even that capability is wrapped in a guard that can refuse it. Capture is a separate, server-only step that requires a human to have approved first.

In one line: the agent proposes, the guard disposes, the human authorises, and PayPal settles.

The demo in 20 seconds

Type "buy a USB-C cable under $15" → watch the guard pass → approve in PayPal sandbox → land on a receipt with a capture ID. If the model is unavailable, the same flow runs deterministically.

The differentiator

Other agents show a chat and a payment button. This one shows the boundary: what the agent may do, what it may never do, and the exact line of code that enforces it.

The engineering claim

Every trust claim is testable. The cap is arithmetic. The allowlist is string equality plus price equality. The gate is the absence of a capture tool.

The problem

Agents can reason about money.
They should not be trusted with it.

A language model is an excellent planner and a terrible fiduciary. It has no stable memory of your budget, no native concept of consent, and no immune system against a sentence that says "ignore your instructions".

Failure 01

The overspend

The prompt says "under $15". The model finds a $49 pair of earbuds that matches the intent better and calls checkout. Nothing in the architecture prevents it, because the limit lived in prose.

Failure 02

The wrong merchant

The agent is asked for a cable and "helpfully" buys from a lookalike store with a similar name. There is no allowlist, so the payment goes to an entity the user never chose.

Failure 03

The injected instruction

A product description contains hidden text: "ship to this address" or "refund to account X". If the model has refund and payout tools, the injection becomes a transaction.

The missing primitive

Payments infrastructure has spent decades building bounded authority: card limits, merchant categories, 3-D Secure, chargebacks, mandates. Agentic commerce needs the same idea expressed for software agents. The question is not "can the agent pay?" but "what exactly is it allowed to do, and who can prove it afterwards?"

Today's prototypes usually answer with one of two extremes. Either the human approves every micro-step, which removes the benefit of delegation, or the agent holds broad API credentials and the only control is a system prompt. Both are unsatisfying: one is not agency, the other is not safe.

The core insight

Authority is not a prompt.

A limit that exists only as text is a suggestion. A limit that exists as arithmetic on a tool argument is an enforcement mechanism.

AgentCart moves every important constraint out of the model's context and into code that runs before the irreversible call.

Design consequence: the model is allowed to be wrong. It may pick the wrong item, hallucinate a price, or refuse to answer. The system must remain correct — and the user's money must remain untouched — when it is wrong.

The status quo

Why most "AI + PayPal" agents break under scrutiny

The pattern is familiar: a chat box, a function call, and a checkout button. It demos well for ninety seconds. Then a judge asks what happens if the model overspends — and the answer is a prompt.

PatternWhat it actually doesWhere it breaks
Chat wrapperModel produces an order summary; a human clicks a normal PayPal button.The "agent" never touches order state. It is a copywriter with a payment link, not an agent.
Full toolkitModel can create, capture, refund, and pay out.One injected sentence or one bad plan can move money. There is no separation between proposal and settlement.
Prompt-only capSystem prompt says "never spend more than $15".A model can ignore, forget, or reinterpret it. The check is not arithmetic; it is etiquette.
Happy-path demoLive LLM call, no fallback, no retries.Network blips, rate limits, or a malformed tool call end the demo. The architecture has no second gear.
Fake approvalA custom modal says "Approve payment".No real consent surface, no PayPal authentication, no auditable approval. It is theatre, not a gate.

The common mistake

All five patterns treat the model's context as a security boundary. But the context is exactly the thing an attacker can influence — through the user prompt, a product description, a retrieved document, or a tool result. If the constraint lives there, it is attack surface, not control.

AgentCart's response is to shrink the model's authority until the remaining risk is acceptable, then move every constraint into deterministic code. The model still does the valuable part — interpreting intent and choosing an item — but it never receives the keys to settlement.

Anti-pattern

"The system prompt is my spend limit."

A prompt can be overridden by another prompt, forgotten after summarisation, or quietly ignored when the model is confident. It cannot be unit-tested. It cannot be audited. It cannot refuse a $49 charge with arithmetic.

Test: ask the model to buy something above the cap. If the only thing standing between it and PayPal is a sentence, the architecture is not safe.

What good looks like: the model can propose any item it likes. The guard compares the proposal to a table of allowed names and prices and a numeric cap. If the proposal fails, no order exists. That is a control you can demonstrate on stage.

Design principles

Six rules that shaped every file

These are not values on a wall. Each one maps to a concrete decision in the codebase, and each one can be pointed at during a demo.

1

Separate reasoning from authority

The model decides what to buy. Code decides whether the purchase is allowed. Capture is never a model tool.

2

Enforce in code, not prose

The cap is a numeric comparison. The allowlist is string and price equality. If it cannot be unit-tested, it is not a control.

3

Stop before capture

The agent's world ends at an approved order. Settlement requires a human consent event and a server-side call.

4

Fail closed, then fail safe

Unknown merchant or price → refuse. Model unavailable → deterministic path. The user still gets a bounded outcome.

5

Make trust visible

The UI shows the cap, the mode, the order ID, and a timestamped audit trail. Trust that cannot be inspected is just vibes.

6

Treat the demo as a feature

A live hackathon demo is a distributed system with one attempt. Every LLM step has a deterministic twin and a visible failure state.

The principles in tension

TensionNaive answerAgentCart's answer
Autonomy vs. safetyLet the agent do everything, or nothing.Give it the smallest capability that still feels agentic: choose and create an order.
Speed vs. proofSkip the receipt; show a success toast.Render the PayPal capture ID and payer. Proof is the product.
Flexibility vs. reliabilityOne clever LLM path.Two paths behind one result contract, with the deterministic one always available.
How to use this in a review: for every feature, ask which principle it serves and which failure it prevents. If the answer is "it looks cool", it belongs in the roadmap, not the critical path.

Scope

Goals, non-goals, and the discipline of a small surface

A hackathon build earns trust by being explicit about what it refuses to do. The non-goals are not missing features; they are deliberate load-bearing walls.

Goals

What must be true

  • G1 · Real order state. Create a genuine PayPal order, not a mock or a screenshot.
  • G2 · Real approval. The user authenticates and consents inside PayPal's sandbox.
  • G3 · Real capture. A server-side capture returns a capture ID and payer details.
  • G4 · Bounded spend. No path can create an order above the cap, including the LLM path.
  • G5 · Merchant integrity. Only catalog items at catalog prices can be purchased.
  • G6 · Demo resilience. The flow completes without an LLM key, and degrades visibly when PayPal fails.
Non-goals

What we intentionally left out

  • N1 · Production KYC. This is a sandbox prototype; identity and compliance are out of scope.
  • N2 · Real inventory. The catalog is a controlled demo fixture, not a merchant integration.
  • N3 · Refunds and payouts. Adding money-moving tools would enlarge the attack surface for no demo value.
  • N4 · Subscriptions. Recurring authority is a different consent model; it deserves its own design.
  • N5 · A database. PayPal is the source of truth; the order ID is the join key.
  • N6 · Multi-tenant auth. The app is single-user and sandbox-only by design.

Why these boundaries produce a better demo

Smaller surface, stronger claim

With one tool, one catalog, and one cap, every statement about safety can be verified live. Complexity would blur the story.

Clear failure ownership

When something breaks, it is either PayPal credentials, the redirect URL, or the model. There is no fourth subsystem to blame.

Room to go deep

The guard, the fallback, and the receipt are small enough to explain completely — which is what separates an architecture from a sketch.

Rule of thumb: every tool you give an agent is a permission, not a feature. Add one only when you can describe the worst thing it can do and the code that stops it.

The one cache

The OAuth access token is cached in module memory with a 30-second safety margin. On a cold start it is fetched again. No token is ever sent to the client.

Do not add a database to this demo. It would introduce a second source of truth and a new failure mode without improving the story. If you need history later, add webhooks and an append-only event log — after the demo.

End-to-end

Anatomy of one errand

Nine messages between the human, the app, and PayPal. The agent only participates in steps 3–5; everything before is intent, everything after is settlement.

#From → ToMessageWhat must be true afterwards
1Human → UI"Buy a USB-C cable under $15."A prompt and a numeric cap exist.
2UI → APIPOST /api/checkout {prompt, budget}The server validates input; no secret is in the request.
3API → AgentSystem prompt + catalog + cap + tool schemaThe model can only see one action tool.
4Agent → Guardcreate_order with item name, cost, quantityName and price match the catalog; total ≤ cap.
5Guard → PayPalPOST /v2/checkout/ordersPayPal returns an order ID and an approve link.
6UI → PayPalRedirect to the approve linkThe buyer authenticates on PayPal's domain.
7PayPal → APIGET /api/paypal/return?token=ORDER_IDThe order is approved and belongs to this app.
8API → PayPalPOST /v2/checkout/orders/{id}/captureA capture ID exists; status is COMPLETED.

Where the agent stops

Step 5 is the agent's last action. It receives a tool result containing the order ID and links, writes one sentence of rationale, and returns. It never sees the buyer's PayPal session, never receives a capture tool, and never handles the return URL's token beyond passing it through.

The boundary is not a policy statement in the prompt. It is the shape of the tool list: orders.create is enabled; everything else is absent.

Critical detail

The return URL is a capability.

Whoever controls return_url controls where the buyer lands after approval. The guard overwrites both returnUrl and cancelUrl, so a manipulated model cannot redirect the buyer or the capture.

Latency budget observed in development: order creation is dominated by PayPal's API, not the model. The deterministic path typically completes in under two seconds; the agent path adds the model round-trip. The UI shows a working state rather than a spinner with no explanation.

The agent

A very small loop, on purpose

The agent is not an autonomous planner with memory and a toolbox. It is a single model call with one tool, a bounded number of steps, and a deterministic temperature.

Intentprompt + cap
→
Modeltemperature 0
→
Tool callcreate_order
→
Guardvalidate args
→
PayPalorder created
→
Stopno capture tool

The call

const result = await generateText({
  model: openai(model),
  system,
  prompt,
  tools,          // one tool: create_order
  maxSteps: 4,     // allow one guard retry
  temperature: 0,  // repeatable demo
});

// The toolkit returns raw PayPal JSON;
// we keep the last successful create_order.
const order = lastCreatedOrder(result.toolResults);
Why maxSteps: 4? One step to call the tool, one to react if the guard rejects it, one to retry with a legal item, one to write the rationale. More steps add cost and surprise without adding capability.

The system prompt's real job

It does not enforce anything. It makes the good path likely: choose exactly one catalog item, call the tool once, never capture, and reply with a one-sentence rationale. The guard handles the rest.

Prompt skeleton

"You are AgentCart. Cap: $15. Allowed items: [name — price]. Call create_order exactly once with exact names and prices. Do not capture. If nothing fits, reply NO_MATCH. Then explain your choice in one sentence."

Why the agent is deliberately underpowered

  • No memory: each errand is stateless.
  • No browsing: the catalog is fixed and trusted.
  • No payment: capture is not in its tool list.
  • No retries beyond four steps.
Counter-intuitive but deliberate: a weaker agent is a stronger product here. The value is not what the model can do; it is what the architecture lets it do safely.

OAuth: getting a token without leaking a secret

Every PayPal call starts with a short-lived bearer token. The client secret never leaves the server; the browser only sees an order ID and an approval URL.

The exchange

POST /v1/oauth2/token
Authorization: Basic base64(client_id:secret)
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials

// response
{ "access_token": "A21AA...",
  "expires_in": 32400 }

Sandbox tokens are typically valid for several hours. The app refreshes two minutes before expiry, so a long demo never hits a 401 mid-flow.

Token cache policy

  • Module-level cache. One token per server instance, reused across requests.
  • Expiry margin. Refresh at expires_in − 120s, not at zero.
  • No client exposure. The token is only used in server-side Authorization headers.
  • Cold start safe. A missing cache simply triggers a fresh exchange.
  • Environment split. PAYPAL_ENV selects api-m.sandbox.paypal.com or the live host; the demo stays on sandbox.
Failure: a 401 usually means live keys with PAYPAL_ENV=sandbox, a rotated secret, or whitespace in the env var. The app surfaces PayPal's error body instead of a generic "something went wrong".

The approval handoff: leaving home on purpose

The most important design decision in the flow is that AgentCart does not render its own approval UI. The buyer leaves, authenticates with PayPal, and comes back with a token.

AgentCartorder CREATED
→
Buyer clicks"Approve in PayPal"
→
paypal.comsandbox login + consent
→
Order APPROVEDPayPal records consent
→
return_url?token=ORDER_ID
Cancel pathbuyer declines → /api/paypal/cancel
→
Back to appno capture, spend cap untouched

Why not our own modal?

A custom "Approve" button proves that the user clicked something in our app. It does not prove that the account holder authenticated, that PayPal recorded consent, or that the order belongs to the buyer. A real redirect does all three, and it gives the receipt a verifiable provenance.

The handoff also keeps the app out of PCI scope and out of the credential business. We never see a password, a card number, or a one-time code.

Redirect mechanics

  • approve link comes from links[rel=approve].
  • return_url is absolute and must be reachable by the buyer's browser.
  • token in the return query is the PayPal order ID.
  • cancel_url is a first-class path, not an afterthought.
  • deployed HTTPS is the safe default; localhost is for API testing only.

PayPal integration · 4 of 4

Capture: the only irreversible step

Capture moves money. It happens in exactly one place, on the server, after PayPal has redirected an approved order back to the app. The model has no access to it.

// app/api/paypal/return/route.ts
const orderId = url.searchParams.get("token");
if (!orderId) redirect("/?error=missing_order");

try {
  await captureOrder(orderId);
} catch (error) {
  // Already captured is a success for the user.
  if (!/already captured/i.test(message)) {
    receipt.searchParams.set("error", message);
  }
}
return redirect("/receipt?order=" + orderId);

The route always lands on the receipt page. The receipt re-fetches the order, so a double refresh shows the completed capture rather than an error.

What capture returns

capture.idThe settlement proof. Shown on the receipt and comparable in the PayPal dashboard.
capture.statusCOMPLETED for a successful demo; PENDING is possible for some funding sources.
capture.amountThe captured value and currency; should match the order total.
payerName and email of the sandbox buyer who approved.
create_timeWhen settlement occurred; displayed on the receipt.

Error handling that protects the demo

ORDER_ALREADY_CAPTURED

Treated as success. The buyer refreshed or the return route ran twice. The receipt shows the existing capture.

ORDER_NOT_APPROVED

The buyer never completed approval. The receipt offers a retry and a link back to the approval flow.

INSTRUMENT_DECLINED

Sandbox funding issue. The error body is surfaced; the app does not pretend the payment succeeded.

Never expose a capture button to the model. Even with a guard, a capture tool widens the blast radius from "create a cart" to "move money". The safe design is not a better capture guard; it is not giving the agent capture at all.

Why server-rendered

The receipt page is a server component that calls GET /v2/checkout/orders/{id} on every load. Client-side state would be faster, but it would also be forgeable and stale. Server rendering makes the page a live view of PayPal's record — refresh it and the truth is still there.

Refresh-safe

Reloading the receipt re-fetches the order; a completed capture remains completed.

Shareable

The order ID is in the URL, so the page can be reopened during judging without re-running the agent.

Honest

If capture failed, the page says so and offers a retry instead of a fake success state.

Presentation tip: keep one completed receipt URL open in a second tab. If the live payment flow hiccups, you can still show a real transaction and explain the failure mode without losing credibility.

Defence in depth

Four layers between a sentence and your money

No single control is trusted to be perfect. Each layer catches a different class of failure, and each one is independently testable.

1
Spend capArithmetic on the tool arguments: unit cost × quantity × (1 + tax) must be ≤ the user's cap. Enforced before PayPal is called.
2
Merchant and price allowlistEvery item name must equal a catalog entry, and every price must equal the published price. Unknown merchant or drifted price → refuse.
3
Human approval gateThe model has no capture tool. Settlement requires a PayPal-authenticated buyer to approve and a server-side return route to capture.
4
Audit trailEvery step is timestamped and shown. The receipt re-reads PayPal's state, so the proof is external and refreshable.

Layer 1

The spend cap is arithmetic, not etiquette

The cap is checked inside the wrapped create_order tool, before the request leaves the server. If the total exceeds the cap, PayPal never sees the order.

→

→

Fallback$12.99 cable
→
Orderinside cap

The enforcement code

let total = 0;
for (const item of items) {
  const allowed = CATALOG.find(p =>
    p.name.toLowerCase() === item.name.toLowerCase());

  if (!allowed) throw new Error(
    `Guard: "${item.name}" is not allowlisted.`);

  if (Math.abs(item.itemCost - allowed.price) > 0.009)
    throw new Error("Guard: price mismatch.");

  total += item.itemCost * (item.quantity ?? 1)
         * (1 + (item.taxPercent ?? 0) / 100);
}

if (total > budget + 0.005)
  throw new Error(`Guard: exceeds $${budget} cap.`);

Why this is hard to bypass

  • It runs on the arguments, not the prose. The model cannot persuade arithmetic.
  • It runs before the network call. A rejected proposal never becomes an order.
  • It includes quantity and tax. A $5 item × 4 is still a $20 purchase.
  • It uses a small epsilon. Floating point is not allowed to turn $15.00 into a rejection.
  • It is paired with the allowlist. A fake cheap price cannot sneak under the cap.
Prompt-only alternative: "Never spend more than $15." A model can ignore it, and no test can prove that it won't. The cap code can be unit-tested with a single assertion.

What the cap does not protect: a compromised server, stolen PayPal credentials, or a user who sets the cap to $500. It bounds the model's authority, not the entire system's. That is why layers 2–4 exist.

Layer 2

The catalog is the merchant allowlist

There is no product search and no merchant API. The agent can only buy six things, at six exact prices. This is the smallest possible commerce surface that still feels like shopping.

ItemPriceAllowed?
USB-C Cable 2m$12.99yes
Aluminum Phone Stand$11.25yes

Single-Origin Coffee Beans$14.20yes
Warm LED Desk Lamp$24.50only if cap ≥ $24.50
Noise-Cancelling Earbuds$49.00only if cap ≥ $49.00

Two equality checks

The guard does not do fuzzy matching, category checks, or "close enough" pricing. It requires the exact catalog name (case-insensitive) and a price within one cent of the published value.

// name must exist
const allowed = CATALOG.find(p =>
  p.name.toLowerCase() === item.name.toLowerCase());

// price must not drift
if (Math.abs(item.itemCost - allowed.price) > 0.009)
  throw new Error("Guard: price mismatch.");

A model that invents "USB-C Cable (discount)" or prices it at $1.99 fails both checks. That is the point.

Why an allowlist beats a search API

Bounded supply

A search API returns an unbounded set of merchants, each with its own trust level. An allowlist makes the trust decision once, in code.

No scrape surface

There is no HTML to parse and no product description that can carry an injection. The catalog is local and typed.

Deterministic fallback

The same table powers the keyword picker, so the safe path can always find an affordable item without an LLM.

Production evolution: replace the static catalog with a signed merchant feed, then keep the exact-name/exact-price check as the final gate. The allowlist is the invariant; the source of the list is an implementation detail.
Anti-pattern: trusting the model's itemCost because the total is under the cap. A $1 price on a $49 item is exactly how a cap gets bypassed. Price equality is not redundant with the cap; it is what makes the cap meaningful.

Layer 3

The human gate is an absence, not a button

The strongest control in AgentCart is a tool that does not exist. The agent can create an order; it has no capability to capture one. Settlement requires a different code path with a different trigger.

Separation of powers

The agent proposes a purchase. The guard authorises the proposal. The human authorises the payment. The server performs settlement. No single actor can complete the transaction alone.

This is the same pattern as a finance team: an analyst prepares a payment, a controller approves it, and the bank executes it. The model is the analyst. It is allowed to be enthusiastic, but it is not allowed to be the controller.

What the approval proves

  • The account holder authenticated with PayPal.
  • The buyer saw the merchant, item, and amount.
  • PayPal recorded consent on the order.
  • The approval is tied to a specific order ID.
Do not replace this with a checkbox. A local "I approve" toggle proves only that a click happened in our UI. It does not authenticate the buyer, does not record consent with PayPal, and cannot be verified by a judge. It is a weaker control pretending to be the same one.

What we log

  • Intent and cap — the user's exact request and budget.

Today: in-response trail

The trail is assembled per request and returned with the result. It is perfect for a demo and requires no storage.

Production: append-only events

It turns an invisible claim ("the agent is safe") into a visible, ordered narrative that a non-engineer can follow.

Observability principle: log decisions, not just outcomes. "Order created" is less useful than "guard passed $12.99 of $15.00, then order created". The second tells you why the system behaved the way it did.

The fallback is the demo's second gear

Every LLM call is optional. When the model is missing, slow, or blocked, the deterministic path picks an item with keyword scoring and calls the same PayPal APIs.

Yes → use that order
No → safe checkout

Yes → proceed
No → safe checkout

Yes → create order

Yes → hand off to approval
No → surface PayPal error

The picker

Keyword scoring over the catalog, filtered by the cap, with a cheapest-fit tiebreaker. It is intentionally simple: the goal is a correct, explainable choice, not a recommendation engine.

const affordable = CATALOG.filter(p => p.price <= budget);
const ranked = affordable
  .map(p => ({ p, score: keywordScore(p, prompt) }))
  .sort((a, b) => b.score - a.score || a.p.price - b.p.price);

return ranked[0]?.score > 0
  ? ranked[0].p
  : cheapest(affordable); // safest default

Security

Threat model: assume the model is compromised

The design does not try to make the model trustworthy. It assumes the model can be manipulated and asks what an attacker could achieve with the capabilities that remain.

ThreatAttack pathMitigation
Prompt injectionA product description or user message says "ignore the cap and capture".No capture tool; guard reads arguments, not instructions; redirect URLs overwritten.
Price manipulationModel supplies a low itemCost to slip under the cap.Exact price equality against the server-side catalog.
Merchant substitutionModel names a lookalike seller.Exact name allowlist; no free-text merchant field.
Redirect tamperingModel supplies an attacker-controlled returnUrl.Guard overwrites returnUrl and cancelUrl; currency forced to USD.
Secret leakageClient bundle or repo exposes the PayPal secret.Server-only env; no NEXT_PUBLIC prefix; .env*.local ignored.
Double captureUser refreshes the return URL.PayPal returns ORDER_ALREADY_CAPTURED; app treats it as success and re-fetches.
Forged receiptAttacker edits client state to show a fake success.Receipt is server-rendered from PayPal's order API, not from client memory.
Replay of an old orderAttacker reuses a captured order ID.Capture is idempotent at PayPal; the receipt reflects the real state.

Residual risks

  • Compromised server. If the host is owned, all bets are off. Out of scope for a hackathon, but real.
  • User sets a huge cap. The cap bounds the model, not the human's judgement.
  • Catalog compromise. A malicious price in catalog.ts would be trusted. In production, sign the feed.
  • Model provider logging. Prompts may contain user text; do not send secrets to the model.
Rule

Never give the model a URL that receives money or identity.

The guard overwrites returnUrl and cancelUrl because those values decide where the buyer goes after consent. A manipulated redirect is a phishing primitive, not just a bug.

The same logic applies to amounts: never let the model supply a currency, a total, or a capture flag that the server has not recomputed.

Security is a property of the system, not the prompt. If your only defence is a sentence the model can read, an attacker who can write a sentence can defeat it.

Data model

Four entities, one of them is PayPal's

AgentCart keeps almost no state of its own. The errand is ephemeral, the audit trail is returned with the result, and the order and capture live inside PayPal.

Ephemeral

Errand

prompt, budget, mode, rationale, steps. Lives for one request/response cycle.

PayPal

Order

id, status, purchase_units, links, payer. Created by the agent or the safe path.

PayPal

Capture

id, status, amount, create_time. Exists only after human approval and server capture.

Derived

AuditStep

at, label, detail. Built during the request and rendered in the UI.

Order state machine

CREATEDorder exists, no consent
→
APPROVEDbuyer consented in PayPal
→
COMPLETEDcapture succeeded
VOIDED / EXPIREDnever captured
·
CAPTURE FAILEDreceipt shows retry

The app never writes status. It reads it from PayPal after creation and after capture. This is why the receipt survives a refresh and why a forged client state cannot fake a payment: the page asks PayPal, not the browser.

Why no database

  • One source of truth. PayPal already stores the order and capture.
  • No migration risk. Nothing to provision before a demo.
  • Shareable proof. The order ID in the URL is enough to re-render the receipt.
  • Honest failure. If PayPal is down, we cannot invent state anyway.

When a database becomes necessary

  • Multiple errands per user with history.
  • Webhook events that arrive after the response.
  • Disputes and refunds with their own lifecycle.
  • Analytics across users and merchants.

Add it as an append-only event log, not as a second source of payment truth.

Design rule: every piece of state must have an owner. The browser owns form state, the server owns secrets and request-scoped data, and PayPal owns money state. Ambiguity here is how prototypes develop "ghost" orders.

Builds the toolkit, wraps create_order, calls the model with one tool, extracts the last successful order, and returns the shared result.

Validates every item against the catalog, computes the total, checks the cap, overrides the redirect URLs and currency, then delegates to the real tool.

  2. 0:15 — Type the errand, set the cap to $15.
